# ADR 0006: LTI 1.3-Only Authentication

## Status
Accepted

Supersedes [ADR 0005](0005-session-based-student-auth.md)'s auth mechanism outright — the
multi-tenant storage design it in turn built on ([ADR 0002](0002-multi-tenant-docker-path-partitioned-storage.md))
is unchanged; only *how a session gets minted* changes again.

## Context
This project is being handed over (not sold) to financially-strapped university
disability-services (ADA) offices for self-hosting. For that audience, the real blocker to
adoption isn't engineering effort on our side — it's whether the office's own (often
under-resourced, and not necessarily supportive) IT department signs off on running it at all.

ADR 0005's session-cookie model is, by its own admission, "security by obscurity": a random,
unguessable token with no password, no recovery, and no second factor. That is exactly the kind of
home-grown auth scheme a campus security review is likely to reject outright — and a rejection is a
much larger blocker for a low-power office than a bounded, well-understood IT task. LTI 1.3 is a
protocol every LMS admin already knows how to evaluate and register; trading a larger engineering
lift on our side for a *smaller, more approvable* ask of IT is the right trade for this audience.

## Decision
Authentication is now LTI 1.3 Resource Link launches, full stop — the old no-signup session cookie
is not kept as a fallback:

1. **`GET|POST /lti/login`** (`LtiLoginHandler`) — OIDC third-party-initiated login. Validates the
   platform's `iss` against the one registered platform (`LtiPlatformConfig`, from
   `CEF_LTI_ISSUER`/`CEF_LTI_CLIENT_ID`/`CEF_LTI_DEPLOYMENT_IDS`/`CEF_LTI_AUTH_LOGIN_URL`/
   `CEF_LTI_JWKS_URL`), mints a state+nonce (`OAuthStateStore`), redirects to the platform's own
   auth endpoint. Rate-limited 5/min/IP, same as `/api/auth/start` was.
2. **`POST /lti/launch`** (`LtiLaunchHandler`) — the platform POSTs back a signed `id_token`.
   `LtiLaunchVerifier` checks the signature against the platform's JWKS, issuer, audience (+`azp`
   for multi-audience tokens per OIDC core 3.1.3.7), nonce, `message_type`/`version`, and that
   `deployment_id` is one we actually registered. This is the *only* place a session is ever
   minted now.
3. **Identity is derived, not random:** `studentId = "lti-" + sha256("iss|deployment_id|sub")`.
   Deriving it from three LTI claims (rather than generating a random token, as before) means the
   same LMS user always maps back to the same tenant — see point 6 below — while leaving
   `TenantDatabaseFactory`'s hash-partitioned storage completely unchanged; it only ever needed *a*
   stable string, not specifically a random one.
4. **Roles decide staff access for free.** The launch's roles claim (checked via `isStaffRole()`,
   a substring match on "Instructor"/"Administrator" IMS role URIs) determines whether a
   `StaffSession` is minted alongside the ordinary `UserSession` — see
   [ADR 0007](0007-staff-console-via-lti-roles.md) for the console this unlocks.
5. **One platform per deployment.** `LtiPlatformConfig` holds a single registered LMS instance, not
   a registry of several — matches this project's existing shape (one self-hosted deployment per
   institution). Supporting more than one LMS instance per deployment is a small, additive
   follow-up (a list instead of one config) if an institution ever needs it, not a redesign.
6. **Re-launch *is* the recovery mechanism.** Because `studentId` is derived from stable LTI
   claims rather than randomly generated, a student who loses their session cookie (clears
   browser data, switches devices) gets back to the exact same tenant simply by clicking the same
   course link again. This directly replaces ADR 0005's deferred "copy/email yourself a recovery
   link" fast-follow — no SMTP dependency for IT to configure, no new workstream needed.
7. **`/api/auth/start` is removed.** `generateStudentId()` (random token generation) is gone.
   `/api/auth/logout` is kept — clearing cookies is still meaningful regardless of how a session
   started.
8. **TLS is now mandatory, not "recommended for real production."** LTI 1.3 requires HTTPS
   launch/redirect URIs — `DEPLOYMENT.md`'s reverse-proxy guidance changes accordingly.
9. **Iframe-launch cookie gotcha, designed around rather than discovered in production:** modern
   browsers (Safari ITP, Chrome's third-party-cookie phase-out) block third-party cookies even
   with `SameSite=None`, and LMSs commonly embed tools in an iframe. `DEPLOYMENT.md` recommends
   configuring the LMS placement as a new-window/new-tab launch instead of trying to solve
   iframe-scoped session storage — the session cookie is then an ordinary first-party cookie.

## Alternatives Considered
* **Keep the ADR 0005 cookie model, unchanged.** Rejected: unlikely to pass a campus security
  review, which is the actual blocker this ADR exists to remove.
* **Keep both — LTI as an added path, cookie link-sharing as a fallback for offices that skip LMS
  registration.** Considered, explicitly rejected: maintaining two parallel auth surfaces (and two
  sets of tests, two mental models for "how does a session start") was judged not worth it once
  the decision was made to fully commit to LTI as the credible, IT-approvable path. An office that
  can't get LTI registered has no path in today — a real cost, accepted deliberately.
* **A separate email/SMTP-based recovery workstream**, as ADR 0005 deferred. Superseded entirely
  by point 6 above — LTI re-launch already solves it, at zero additional infrastructure cost.
* **Generic SAML/OIDC SSO instead of LTI.** Rejected: doesn't get automatic LMS course/module
  embedding the way LTI does, which is the actual point of choosing LTI over a bare IdP
  integration for this audience.

## Consequences

### Positive
* No more home-grown, obscurity-based auth for a campus security review to flag.
* Session recovery is solved for free (point 6) — no SMTP dependency, no separate workstream.
* Instructor/staff role recognition comes for free from the same launch (see ADR 0007) — no
  separate staff credential store to build or operate.

### Negative
* **No more zero-IT-touch deployment.** The old model's headline property — an ADA office could
  stand this up without asking IT for anything — is gone. Registering an LTI tool (issuer, client
  id, deployment id, JWKS URL) is now a required, one-time IT task. Accepted deliberately: it's a
  smaller, more familiar ask than "please approve our custom auth scheme."
* Direct, non-LMS-embedded access (e.g. bookmarking the app URL, using it outside any course
  context) is no longer possible — a real capability loss from ADR 0005's model, not just a
  friction increase.
* TLS is now a hard requirement rather than a "recommended for production" note, which is one more
  thing that has to be true before a deployment works at all.
* `AuthSessionIntegrationTest.kt` (the old cookie-model's test coverage) was replaced by
  `LtiLaunchIntegrationTest.kt` — anything relying on `/api/auth/start` in tests
  (`AgentStreamTest`, `StudentIdRoutingTest`, `ApplicationTest`) needed updating to launch via a
  locally-signed test JWT (`LtiTestSupport`) instead.
